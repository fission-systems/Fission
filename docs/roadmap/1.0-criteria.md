# 1.0.0 criteria (draft, 2026-10-31)

Status: draft for the maintainer to accept, change or reject. Every claim is
tagged **verified** (checked in the tree or by running it on 2026-10-31) or
**unverified**. Nothing here is a release decision.

## What 1.0.0 would promise

Fission is **agent-first**: there is deliberately no GUI or TUI (both were built
once and removed on purpose), and the product is the headless CLI plus its JSON
contract. `docs/VERSIONING.md` already defines a `0 -> 1` change as a break of the
documented CLI contract, the stable artifact schemas, or the installation layout.
So 1.0.0 is a statement about three things only:

1. the **commands** an agent can rely on,
2. the **shape of their JSON output** and exit codes,
3. the **platforms and binary kinds** those promises cover.

It is not a promise of a stable Rust library API (`docs/EVALUATION.md` says so
today and should keep saying so), of readable pseudocode on every function, or of
parity across every architecture and file format.

## The promised surface

| Command | State |
|---|---|
| `info`, `list`, `disasm`, `decomp`, `strings`, `xrefs`, `hex`, `search`, `patch`, `inventory` | exist (verified, `docs/CLI.md`) |
| `db` (names, signatures, notes, breakpoints, revisions, undo/redo, diff) | exists (verified) |
| `script` (Rhai, read-only) | exists (verified) |
| `debug` (emulator, Linux ptrace, macOS native, Windows native behind a feature) | see "Debugger" below |
| `schema` (envelope and error-code schemas) | exists (verified) |

## Blockers, in the order they matter for an agent-first 1.0

1. **Per-command `data` schemas are untyped.** Only the envelope is typed; the
   envelope schema marks `data` as `x-data-schema: untyped` (verified,
   `docs/CLI.md`, "Machine contract"). Under an agent-first promise the contract
   *is* the product: `info`, `list`, `decomp`, `xrefs`, `strings`, `search`, `db *`
   and `inventory *` each need a versioned schema, committed under
   `docs/schemas/`, with a test that fails when the output drifts from it.
2. **The contract is opt-in.** `--contract v1` (or `FISSION_CONTRACT=v1`) is
   required; without it every command prints the human form (verified). 1.0 has
   to decide: make v1 the default, or promise that opt-in forever.
3. **Compatibility shims.** Legacy flat invocations are "supported for one
   transition period" and `--layer`, `mlil-preview`, `--compiler-id`, `--format`,
   `--engine` are accepted and ignored or dead (verified in `docs/CLI.md`; the
   last three per issue #455, unverified here). Remove them or put a date on them
   before they become part of a 1.0 promise.
4. **Cost per call.** Each CLI invocation reloads and re-analyses the binary.
   Measured on the 233-row sample set (2026-10-30): median 0.24 s, 2-3 s on
   binaries with thousands of functions. **Re-measured 2026-11-12** on a release
   build of main (wall clock, min of 3, `list`/`hex`/`decomp --addr`/`xrefs`/
   `strings --context`, ELF only): 0.01 s for a 28 KB binary with 23 functions;
   0.07-0.09 s for bash O0 (3 MB, 2,884 functions); 0.12-0.14 s for the largest
   corpus ELFs (4-6 MB, up to 4,188 functions). Every command costs about the same
   as `list`, so the load dominates and the per-command work does not. The
   earlier 2-3 s figure no longer reproduces on ELF; it predates the startup work
   in #699-#701. **Not measured:** PE and Mach-O (the local corpus is 803 ELFs),
   and cost on one very large function (that is per-function work, not reload). At
   ~0.1 s a call, a resident session or analysis cache buys little for an agent
   that makes dozens of calls, so it is not built; revisit if a PE or Mach-O
   measurement or a larger image says otherwise. `fission-analysis-protocol`
   already defines local-HTTP backend contracts that nothing in the CLI uses
   (verified).
5. **Provenance in results.** Issue #660 reports evidence-traceability gaps in a
   PE64 workflow (unverified; not read). An agent can only trust a result that
   says where it came from.
6. **Agent guidance artifact.** [`skills/fission/SKILL.md`](../../skills/fission/SKILL.md)
   is a usage guide for agents, written from commands run against the current
   CLI. `fission_cli skill` prints it from the binary, and a unit test holds every
   command, flag and error code it names to the real CLI. What is still open: it
   is one file, not split into topics the way `kuna docs` is, and it is not
   installable into an agent's skills directory by a command.

## Debugger

* Emulator: the cross-platform default (verified).
* Linux `ptrace`: launch, attach, step, breakpoints, registers, memory, modules
  (verified in code and by the Linux CI job).
* macOS: `ptrace` for control, the Mach task port for state (PRs #704, #707).
  **Verified** on Apple Silicon, macOS 26.5.1: seven live tests against real
  processes (launch to exit code, single step, breakpoint hit / hidden original
  bytes / step-off / exit, breakpoint removal, memory and register writes,
  module list after dyld, attach and detach), 100 consecutive runs, 0 failures.
  It needs two things on the machine: the `fission_cli` binary signed with the
  `com.apple.security.cs.debugger` entitlement (`scripts/macos/sign-debugger.sh`,
  redone after every rebuild) and `sudo DevToolsSecurity -enable` once.
  **Not covered:** multi-threaded targets, hardware breakpoints and watchpoints,
  x86-64 hosts, and signing of the shipped macOS archive. The live tests run by
  hand (`scripts/macos/run-live-debugger-tests.sh`), not in CI.
* Windows native: behind `--features windows_native_debugger`; 29 open `area:dynamic`
  issues describe WOW64/32-bit defects (unverified individually). Either fix them
  or keep Windows live debugging out of the 1.0 promise.

## Support matrix, measured (2026-11-13)

Unmeasured cells should not be promised, so every cell was measured. One small
C program (`scripts/quality/support_matrix_prog.c`: a loop, a switch, a byte
scan, recursion, a string, a libc call) was cross-compiled at `-O1` for each
cell with mingw-w64 (PE x64/x86), zig (PE ARM64, MIPS, PPC, RISC-V, ARM) and the
host clang (Mach-O). `scripts/quality/support_matrix_probe.py` then ran `info`,
`list`, `strings`, `disasm` and `decomp --all` on each under `--contract v1`.

This measures **"does it work at all"**, never "is the pseudocode right". The one
content check counts functions whose output calls a tiny-address `sub_N()`
(address `0x1`-`0xfff`): that is never real code, it is a p-code internal branch
that was read as a machine address.

| cell | loads, lists, disassembles | `decomp --all` returns code | functions calling a tiny `sub_N()` |
|---|---|---|---|
| ELF x86-64 | yes | 54/54 | 0 |
| ELF x86-32 | yes | 56/56 | 1 (`__udivmoddi4`) |
| ELF ARM32 | yes | 69/69 | 0 |
| ELF AArch64 | yes | 66/66 | **24/66** |
| ELF MIPS32 BE / LE | yes | 66/67 | **21/67** |
| ELF PPC32 | yes | 67/67 | 1 |
| ELF PPC64 LE | yes | 53/53 | 0 |
| ELF RISC-V 64 | yes, but **names lost** (below) | 3158/3158 | 3 |
| PE x64 | yes | 77/77 | 0 |
| PE x86 | yes | 76/76 | 0 |
| PE ARM64 | yes (no symbols: the linker strips them) | 531/531 | **239/531** |
| Mach-O x86-64 | yes | 5/6 | 0 |
| Mach-O arm64 | yes | 5/6 | **3/6** |

What the table shows:

* **Every cell loads and decompiles without a hard failure.** None of the
  "unmeasured" cells is broken at the container level.
* **x86-64, x86-32, ARM32 and PPC64 (ELF), and PE x64/x86, are clean** on this
  probe. ELF x86-64, x86-32, ARM and PE x64 are also the cells DecBench or the
  checked-in samples cover.
* **AArch64, MIPS and PE ARM64 have a real defect.** The tiny-address calls come
  from one cause: an instruction-internal conditional (AArch64 `csel`, `cinc`,
  `cset`; MIPS equivalents) lifts to a `CBranch` whose destination is a
  non-constant varnode in the current space, so `relative_pcode_target_seq`
  (`fission-sleigh/src/runtime/function.rs`) rejects it (it requires
  `space_id == 0 && is_constant`) and the CFG treats "branch 2 ops forward" as
  "branch to address 2". The visible result is a phantom `sub_2()` call **and a
  lost select**: `sum_to` came back as `return n + ...` without the `n < 0 -> 0`
  arm that `csel` encodes. Reproduced with both the 12.0.4 and the 12.2 `.sla`
  snapshot, so it predates the snapshot move. Not fixed here.
* **RISC-V symbol names are lost** when the binary comes from LLVM tooling. The
  ELF symbol table has 11,220 entries, 11,075 of them `NOTYPE LOCAL` (`.L0 `,
  `.Lpcrel_hiN`, `$x`). They are listed as 3,158 "functions", and a local label
  wins the name at an address where a real `FUNC` symbol sits (`classify` at
  `0x1001e38` is listed as `.L0 `; `main` is absent). Not fixed here.
* **Mach-O lists `__mh_execute_header` as a function**, and that is the one
  function without code in both Mach-O rows.

Caveats: -O1 only; one tiny program; the toolchains are zig/mingw/clang, not
each platform's native compiler; "returns code" includes wrong code (the AArch64
`csel` case above returns code).

### Recommended matrix for 1.0 (for the maintainer to accept)

| tier | cells |
|---|---|
| **Promised** | ELF x86-64, x86-32, ARM32/Thumb; PE x64, x86 |
| **Best effort (documented, not promised)** | ELF AArch64, MIPS, PPC32/64, RISC-V; PE ARM64; Mach-O x86-64, arm64; NE, a.out, Intel HEX, Motorola HEX |

AArch64 would move to "promised" once the `csel` branch defect is fixed and
remeasured; it is the most common non-x86 target and the cell where this
defect costs the most (36% of functions in the probe).

## Out of scope for 1.0 (proposed)

* Any GUI/TUI (by design).
* The plugin API: issue #557 reports zero production implementations and #451 a
  use-after-unload; the `script` command and the CLI are the extension points for
  an agent. Remove it from the promise or hide it.
* Roughly 70 of the 250 open issues are roadmap-style feature requests (hooking
  engine, fuzzing engine, CRDT collaboration, MCP bridge, ...), by a title
  heuristic. They are not defects and should carry a post-1.0 label rather than
  count against readiness.

## The defect backlog

250 open issues on 2026-10-31, about 180 defect-like. They are detailed audit
reports, three to five claims each. Spot checks so far: of the claims examined,
some were real (`search` truncating 64-bit values, `strings_array` ignoring
`min_len`, an unconditional `/tmp` write in function discovery; fixed in #703 and
#705), some were already fixed (#191, #327, the `strings` part of #455), and some
were not true of the current code (#425's `PE64` format string; the PE loader
reports `PE`). **No claim should be assumed true or false without a check.** The
areas with the most open defect reports are loader (30), emulator JIT (21), pcode
(14), decompiler (13), static (13), signatures (12), dynamic (11).

Suggested rule for 1.0: an open defect blocks the release only if it is in the
support matrix above and has a reproduction.

## Decisions needed from the maintainer

1. **Is `--contract v1` the default in 1.0?** Recommended: **no, keep it
   opt-in, and say so in the promise.** Facts: contract mode requires the
   command's own `--json` (without it the supervisor fails with `json_required`),
   so making it the default would break every invocation that does not pass
   `--json`. 12 scripts, 4 workflows and 15 integration-test files reference
   the CLI (not counted: which of them already pass `--json`), and every human at
   a terminal runs it without. An agent loses
   nothing by opting in once (`FISSION_CONTRACT=v1`, which `fission_cli skill`
   documents). The 1.0 promise would be: *`--contract v1 --json` output, its
   envelope, exit codes and error codes are stable; the human-readable form is
   not covered.* That also leaves room to make v1 the default in a later major
   version without having promised the opposite.
2. **Which matrix cells are promised?** Recommended: the table above.
3. Resident session, on-disk cache, or neither, for call cost?
4. Plugin API: remove, hide, or keep out of the promise?
5. Does Windows live debugging ship in 1.0? (The two failing Windows debugger
   tests are fixed as of #840; the WOW64 issue list is closed.)
