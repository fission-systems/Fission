    1.0.0 criteria (draft, 2026-10-31)¶

    Status: draft for the maintainer to accept, change or reject. Every claim is tagged verified (checked in the tree or by running it on 2026-10-31) or unverified. Nothing here is a release decision.

    What 1.0.0 would promise¶

    Fission is agent-first: there is deliberately no GUI or TUI (both were built once and removed on purpose), and the product is the headless CLI plus its JSON contract. docs/VERSIONING.md already defines a 0 -> 1 change as a break of the documented CLI contract, the stable artifact schemas, or the installation layout. So 1.0.0 is a statement about three things only:

    1. the commands an agent can rely on,
    2. the shape of their JSON output and exit codes,
    3. the platforms and binary kinds those promises cover.

    It is not a promise of a stable Rust library API (docs/EVALUATION.md says so today and should keep saying so), of readable pseudocode on every function, or of parity across every architecture and file format.

    The promised surface¶

    Command State
    info, list, disasm, decomp, strings, xrefs, hex, search, patch, inventory exist (verified, docs/CLI.md)
    db (names, signatures, notes, breakpoints, revisions, undo/redo, diff) exists (verified)
    script (Rhai, read-only) exists (verified)
    debug (emulator, Linux ptrace, macOS native, Windows native behind a feature) see "Debugger" below
    schema (envelope and error-code schemas) exists (verified)

    Blockers, in the order they matter for an agent-first 1.0¶

    1. Per-command data schemas are untyped. Only the envelope is typed; the envelope schema marks data as x-data-schema: untyped (verified, docs/CLI.md, "Machine contract"). Under an agent-first promise the contract is the product: info, list, decomp, xrefs, strings, search, db * and inventory * each need a versioned schema, committed under docs/schemas/, with a test that fails when the output drifts from it.
    2. The contract is opt-in. --contract v1 (or FISSION_CONTRACT=v1) is required; without it every command prints the human form (verified). 1.0 has to decide: make v1 the default, or promise that opt-in forever.
    3. Compatibility shims. Legacy flat invocations are "supported for one transition period" and --layer, mlil-preview, --compiler-id, --format, --engine are accepted and ignored or dead (verified in docs/CLI.md; the last three per issue #455, unverified here). Remove them or put a date on them before they become part of a 1.0 promise.
    4. Cost per call. Each CLI invocation reloads and re-analyses the binary. Measured on the 233-row sample set (2026-10-30): median 0.24 s, 2-3 s on binaries with thousands of functions. An agent that queries one binary dozens of times pays this each time. A resident session or an on-disk analysis cache is the natural answer; no resident mode exists today (searched the CLI argument definitions, unverified beyond that). fission-analysis-protocol already defines local-HTTP backend contracts that nothing in the CLI uses (verified).
    5. Provenance in results. Issue #660 reports evidence-traceability gaps in a PE64 workflow (unverified; not read). An agent can only trust a result that says where it came from.
    6. Agent guidance artifact. There is no skills/ directory or installable usage guide (verified). Kuna ships one inside its binary.

    Debugger¶

    • Emulator: the cross-platform default (verified).
    • Linux ptrace: launch, attach, step, breakpoints, registers, memory, modules (verified in code and by the Linux CI job).
    • macOS: ptrace for control, the Mach task port for state (PRs #704, #707). Verified on Apple Silicon, macOS 26.5.1: seven live tests against real processes (launch to exit code, single step, breakpoint hit / hidden original bytes / step-off / exit, breakpoint removal, memory and register writes, module list after dyld, attach and detach), 100 consecutive runs, 0 failures. It needs two things on the machine: the fission_cli binary signed with the com.apple.security.cs.debugger entitlement (scripts/macos/sign-debugger.sh, redone after every rebuild) and sudo DevToolsSecurity -enable once. Not covered: multi-threaded targets, hardware breakpoints and watchpoints, x86-64 hosts, and signing of the shipped macOS archive. The live tests run by hand (scripts/macos/run-live-debugger-tests.sh), not in CI.
    • Windows native: behind --features windows_native_debugger; 29 open area:dynamic issues describe WOW64/32-bit defects (unverified individually). Either fix them or keep Windows live debugging out of the 1.0 promise.

    Support matrix to decide¶

    Unmeasured cells should not be promised.

    x86-64 x86-32 AArch64 ARM/Thumb MIPS/PPC/other
    ELF measured (DecBench) measured (6 rows) measured measured (71 rows) unmeasured
    PE measured (checked-in samples) unmeasured unmeasured - -
    Mach-O unmeasured - unmeasured - -

    "Measured" means it appears in the DecBench sample set or the checked-in samples, not that its output is good. Loaders for NE, a.out, Intel HEX and Motorola HEX exist (verified) with open defect reports (#432-#434); they are good candidates for "best effort, not promised".

    Out of scope for 1.0 (proposed)¶

    • Any GUI/TUI (by design).
    • The plugin API: issue #557 reports zero production implementations and #451 a use-after-unload; the script command and the CLI are the extension points for an agent. Remove it from the promise or hide it.
    • Roughly 70 of the 250 open issues are roadmap-style feature requests (hooking engine, fuzzing engine, CRDT collaboration, MCP bridge, ...), by a title heuristic. They are not defects and should carry a post-1.0 label rather than count against readiness.

    The defect backlog¶

    250 open issues on 2026-10-31, about 180 defect-like. They are detailed audit reports, three to five claims each. Spot checks so far: of the claims examined, some were real (search truncating 64-bit values, strings_array ignoring min_len, an unconditional /tmp write in function discovery; fixed in #703 and

    705), some were already fixed (#191, #327, the strings part of #455), and some¶

    were not true of the current code (#425's PE64 format string; the PE loader reports PE). No claim should be assumed true or false without a check. The areas with the most open defect reports are loader (30), emulator JIT (21), pcode (14), decompiler (13), static (13), signatures (12), dynamic (11).

    Suggested rule for 1.0: an open defect blocks the release only if it is in the support matrix above and has a reproduction.

    Decisions needed from the maintainer¶

    1. Is --contract v1 the default in 1.0?
    2. Which matrix cells are promised?
    3. Resident session, on-disk cache, or neither, for call cost?
    4. Plugin API: remove, hide, or keep out of the promise?
    5. Does Windows live debugging ship in 1.0?
